Existing template design that all WPs must preserve:
- A template is an ordinary `.twbx` + `template.json` manifest (`format: py-tbparse-template`, `version: 1`).
  Data and extracts stripped, credentials scrubbed.
- `apply_template(template, data, mapping, params, output_path, datasource, data_datasource, allow_missing, overwrite, report)`
  keeps each field's local name (what sheets/formulas use) and only changes the physical column (`remote-name`)
  and the connection. Outputs never overwrite inputs. `template-answers.json` is written into every output
  but nothing reads it back yet.
- Mapping is a DataFrame with `MAPPING_COLUMNS` (`datasource, field, caption, datatype, required, used_by,
  mapped_to, data_type, status, score`), loadable/editable via `load_mapping`.
- Errors are `TemplateError(ValueError)`. Public API is exported from `py_tbparse/__init__.py`.

## 1. Research: what BI users get from templates elsewhere, and what they ask for

Findings first, then how each maps to a WP. Sources at the end of the section.

### 1.1 What already works well in other tools (copy these ideas)

| Tool | Feature | Relevance |
|---|---|---|
| Tableau Accelerators | Data Mapper: each template field (From) is matched to a data field (To) of the **same data type**, incompatible ones greyed out. Since 2023.2 the mapper **saves selections** so you can resume. Unmapped fields break the dashboards using them. | We have the type-checked mapping and broken-sheet report. Missing: resume/save the mapping across sessions (WP3), a re-usable mapping profile (WP1). |
| Tableau Replace Data Source / Replace References | Auto-maps by name + type; unmapped fields show a red `!`; "Replace References" remaps every use (sheets, filters, calcs) in one go. | Our model already covers this. Lesson: users judge a tool by what it does with the **leftovers**, so every WP reports leftovers. |
| Looker Studio replace-data-source | Maps old to new fields by **field ID, name and other configuration**, at component, page or report level. | Match on more than the name: id/alias/caption/type/role (WP1 matcher improvements); scope replacement per sheet/dashboard (backlog idea, WP4 optional). |
| Power BI `.pbit` | No data in the file; **asks for parameter values and credentials on open**; carries parameters, relationships, calcs. | We ask for parameters. Credentials must never be stored; they are entered at use time (confirmed design). |
| Power BI template apps (AppSource) | ISV **pre-fills parameters through a link / automation**, user only authenticates. | Non-interactive "answers file" for apply and batch (WP1, WP4). |
| Power BI deployment pipelines | Parameter rules per environment (dev/test/prod). **Known gaps: parameters of type Any and Text-with-list are not supported.** | Named **profiles** in the answers file (WP1); validate parameter types up front and say what is unsupported rather than failing late. |
| Power BI PBIP / TMDL | Text-first, folder format; diffs cleanly in pull requests, branch/merge works, "thin report" points at a remote model. | Motivates the byte-preserving writer / normalised diff (WP8) and publishing a template as readable text (WP2/WP5 reports). Thin-report idea: apply a template to a **published datasource** (WP4 stretch). |
| Metabase serialization | Export to YAML with **stable entity IDs**, staging to production import. | Stable ids in the manifest are what make `template update` and three-way merge possible (WP1, WP3). |
| Tableau Migration SDK / Content Migration Tool | Transformers for bulk edits: **replace table/schema names, set connection info, set calc formulas, change published data source**, "customer-specific edits". | Real demand: swap a **live DB connection** (server/db/schema/table), not only CSV. Today we only write CSV and workbook-borrowed connections (WP4 "connection targets"). |
| Tableau calculation sharing | Copy/paste calcs between workbooks (one folder at a time); **identical duplicates are skipped, same-name-different-definition are imported and renamed**. Teams keep a "calculations template workbook". | Exact semantics to copy for the library WP (WP6). |
| Style guides (palettes, fonts, header/footer, Format > Workbook, Copy Formatting, `Preferences.tps`) | Organisations keep a style-guide workbook; custom palettes live in `Preferences.tps`; Power BI does the same with theme JSON. | Style-template WP (WP7), including `.tps` palette export/import. |

### 1.2 What people complain about / say they want (the gaps)

1. **Field mismatch breaks everything**: names, types or data roles differ ("customer-id" vs "customer_id"), calcs and views break, red `!` fields. They want better auto-matching and a clear list of what will break **before** applying. (We have broken-sheet report; improve the matcher and report calcs/filters/sets too, WP1.)
2. **Reuse means recreating from scratch**: people with finished multi-dashboard workbooks want to point them at new data without losing calcs, parameters, formatting. (Core feature; keep.)
3. **Settings silently reset** on replace (default properties, etc.). Our diff of "what changed besides the connection" should be a first-class report (WP1 `explain`).
4. **Aggregation level differs**: user data is at a different grain than the template's. Cannot fix, but can warn: detect when the template needs dimensions the data lacks, or key columns are not unique (WP1 checks, WP3).
5. **Excel is the default data source of non-technical users**: Tableau imports every sheet but formulas are not imported and the file needs refreshing. They want "just point it at my xlsx" with sheet choice (WP2).
6. **Many customers/entities, one template**: agencies/ISVs want a folder of inputs to produce a folder of outputs plus a summary (WP4).
7. **Template drifts after it has been used**: authors improve the template; users want to pull the improvement into workbooks built from it without redoing mapping (WP3).
8. **Reusable pieces, not whole workbooks**: calc/parameter libraries and styles (WP6, WP7). Tableau only copies one at a time.
9. **Reviewability**: PBIP shows people want diffable artefacts. We re-serialise XML so every line differs (WP8).
10. **Trust**: "does it open?" is the first question anyone will ask. WP0.

### WP1. Foundation: answers/profile format v2, stable ids, better matcher, `explain`

Everything below depends on this; keep it small and well-tested.

1. **Stable field ids in the manifest** (manifest `version: 2`; loader accepts 1 and 2, writes 2). Per field:
   keep `name`, add `uid` = hash of (datasource name, field local name, role, datatype) so a rename of the
   caption does not change identity. Add `template.id` (UUID made at `make` time and kept on `update`) and
   `template.revision` (int, incremented by `template update`). Backwards compat test with a v1 template from 0.4.0
   (commit one as a fixture).
2. **Answers file v2** (`template-answers.json`, and also standalone `*.answers.json` usable as input):
   adds `template.id`, `template.revision`, per-datasource entries (today it holds one), `profiles`
   (named override sets: `{"prod": {"parameters": {...}, "data": "..."}}`), and `schema_fingerprint` of the data
   (column names + types) so later steps can detect drift. **Never store credentials**; add a test that
   fails if any key named `password|username|token|secret` is serialised. Document that credentials are entered
   in Tableau on open, like Power BI.
3. **`apply_template(..., answers=path|dict, profile=None)`**: non-interactive mode, answers pre-fill mapping
   and parameters; explicit args win over answers; unknown parameter names fail with the list of valid ones
   (mirrors Power BI template-app automation).
4. **Matcher improvements** in `suggest_mapping` (reuse `_match_key` and `compare_field_schemas` from `rename.py`):
   match on caption and alias as well as name, normalise separators (`customer-id` vs `customer_id`) using the
   existing acronym/case logic, add status `role-differs` (dimension vs measure), and score ties get a
   deterministic order. Keep `score` semantics; do not change statuses that existing tests assert.
5. **Granularity/uniqueness warnings** (new `check_data(template, data, mapping) -> DataFrame`): required dimension
   missing, key-looking column with duplicates (read the full CSV for uniqueness only on request, `--deep`),
   empty required column. Informational; never blocks apply.
6. **`explain(template, data, mapping) -> DataFrame`**: everything that will change besides the connection
   (field types changed, fields dropped, calcs that reference unmapped fields, filters/sets on unmapped fields,
   sheets/dashboards affected). Extend `broken_sheets` (currently sheets only) to name the calcs, filters, sets and
   parameters impacted using `usage.field_usage`. CLI: `template apply --explain`.
- Tests: v1 manifest loads; v2 round-trip; answers drive a no-flags apply producing identical bytes to the flagged call
  (modulo timestamp, make timestamps injectable); credentials never serialised; matcher cases (hyphen/underscore,
  caption match, role-differs, non-Latin names, ties).
- Acceptance: all 26 existing template tests unchanged and green.

### WP2. Excel input for templates (backlog: "read Excel files directly")

- `read_data(path, datasource=None, sheet=None)`: support `.xlsx`, `.xlsm`, `.xls`. Add optional extra
  `excel = ["openpyxl>=3.1"]` (and `xlrd` for `.xls` only if the owner wants it; default: `.xlsx/.xlsm` only,
  say so in the error for `.xls`). No hard dependency: import lazily, raise `TemplateError("install py-tbparse[excel]")`.
- Sheet selection: `sheet=` name or index; if the workbook has several visible sheets and none is chosen,
  fail listing them (mirror the "several datasources need a choice" error). Hidden sheets ignored unless named.
- Header detection: first non-empty row; skip blank leading rows; reject merged-header sheets with a clear message;
  dedupe duplicate headers with a suffix and say so. Read `nrows=2000` like CSV for type inference.
- Type inference: reuse `_infer_csv_type`; handle Excel dates/datetimes natively (pandas gives `datetime64`).
- **Connection writer**: write an `excel-direct` connection with one relation per sheet. Study how real
  Tableau writes it **from the corpus** (`tests/corpus/files`, search `class='excel-direct'`; both legacy and
  object-model/relationship forms exist, like `_csv_connection(modern=...)`). Mirror `_csv_connection` structure;
  reuse `_REMOTE_TYPE`; add `_excel_connection(data, local_of, modern)`. Sheet name in the relation is
  `[Sheet$]` style: copy exactly what the corpus shows, do not invent.
- `DataSource` gets `sheet: Optional[str]`; answers record it; CLI `--sheet`.
- Tests: tiny xlsx fixtures built with openpyxl in `tmp_path` (no binary fixtures committed except if a real
  Tableau-written excel-direct workbook is needed for the connection test, then take one from the permissive corpus);
  multi-sheet error; header offset; duplicate headers; date columns; missing extra gives the install hint.
- Risks: connection XML is unverified in Tableau (WP0); Excel number-formatted text; very large sheets
  (cap rows read for inference, state it).

### WP3. `template update` from saved answers (backlog)

Goal: author improves the template (new revision); user re-applies it to the same data/mapping and learns what changed.

- `template update NEW_TEMPLATE WORKBOOK [--write PATH]` where WORKBOOK is an output carrying `template-answers.json`.
  API: `update_from_answers(template, workbook, output_path=None, overwrite=False, report=None) -> str`.
- **Stage A (ship first): what-changed report only**, no write. `diff_template_revisions(old_manifest, new_manifest)`:
  fields added/removed/renamed (by `uid`, falls back to name), required flag changes, type changes, parameter
  added/removed/changed default or allowed values, sheets/dashboards added/removed. Then classify against the
  saved mapping: `auto-carry` (field unchanged and mapped), `needs-mapping` (new required field),
  `orphaned` (mapping targets a removed field), `type-conflict`.
- **Stage B: re-apply**: run `apply_template(new, data_from_answers, mapping=carried, params=carried)`, then stop and
  list `needs-mapping` rows; `--allow-missing` as today. If the data file moved or its schema fingerprint changed,
  say which columns vanished/appeared and re-suggest only for those.
- **Stage C (only if the owner asks): three-way merge** (template-old, template-new, user-edited workbook) in the
  spirit of Copier's update. Needs stable ids on sheets/dashboards/calcs, not only fields: design note first,
  no code until agreed. Detect user edits as `diff.py` differences between the template-old applied with the same
  answers and the user's workbook.
- Detect when the saved `manifest_sha256` matches the new template (no-op, say so) and when answers are from a
  different `template.id` (refuse).
- Tests: add a field, remove a field, rename a caption, change a parameter default, change a type; moved data file;
  answers from another template; stage A output table snapshot.

### WP4. Batch apply: one template, many data files (backlog) + connection targets

- `apply_template_folder(template, directory, patterns=("*.csv","*.xlsx","*.twb","*.twbx"), output_dir=None, mapping=None, params=None, profile=None, on_error="skip"|"stop", report=True) -> DataFrame`
  following `batch.scan_folder` (glob.escape, sorted, warn-and-skip a bad file). Result: one row per input with
  `input, output, status, mapped, missing, broken_sheets, warnings, error`. Always write the summary CSV beside the outputs.
- Name outputs deterministically (`<template>_<input stem>.twbx`), never overwrite unless `overwrite=True`; clash on stem
  across extensions gets a numeric suffix.
- Mapping per file: default auto-suggest per file; with `mapping=` apply the same one and fail files that lack
  mapped columns; with `answers` use their saved mapping as a **prior** and re-suggest only for unmatched columns.
  Add a **tolerance gate**: `--min-mapped 0.9` or "required fields must all map" (default) so a wrong file does not
  silently produce a half-broken workbook.
- Per-file parameters from a sidecar: `inputs.csv` with columns `file, <param captions...>` (agency use case: each
  customer gets its own title/ID parameter). Document it in the README.
- CLI: `py-tbparse template apply-folder TEMPLATE DIR -o OUT [--parallel N]`; parallelism only via
  `concurrent.futures.ProcessPoolExecutor` and only if outputs are independent (they are); default serial.
- **Connection targets (stretch, ask the owner before starting)**: Tableau Migration SDK users replace
  server/db/schema/table. Add `read_data` kinds `sql-table` described by a small YAML/JSON
  (`{"class": "postgres", "server": ..., "dbname": ..., "schema": ..., "table": ..., "columns": [...]}`) with no credentials
  and a `--live` flag; and published-datasource target (`sqlproxy`, the Power BI "thin report" analogue). These are
  unverified against Tableau (WP0) so ship behind an `experimental` note.
- Tests: folder with good, bad, wrong-schema files; summary frame; no overwrite; sidecar params; tolerance gate.

### WP5. Template catalogue and quality (small, high value)

Not in the backlog; the research suggests users first need to **find and trust** templates.
- `template check TEMPLATE`: lint: required fields with no usage, hard-coded server/paths left in, parameters without

- Do not build a registry or sharing service.

### WP6. Calculated-field and parameter libraries (backlog)

Goal: export calcs/parameters from one workbook, import into another, with dependency and clash handling that
Tableau's one-at-a-time copy/paste lacks.

- **Format**: `*.library.json` (`format: py-tbparse-library`, `version: 1`): entries `{kind: calc|parameter|set|group|bin, uid, name, caption, datatype, role, formula, refs: [field/param/calc names], params: [...], folder, comments, source}`. Formulas keep Tableau's internal `[Calculation_123]` form plus the caption form for humans.
- **Export**: `export_library(parser, select=None|names|folder, with_dependencies=True) -> dict/file`. Resolve transitive dependencies with the same reference parsing as `usage._refs` (do not write a second parser); select by folder (the thing Tableau needs shift-click for); report **external references** (fields of the source data the calc needs) as the library's *required fields*, reusing the template manifest idea.
- **Import**: `import_library(parser_or_path, library, mapping=None, on_clash="skip-identical|rename|overwrite|fail", datasource=None, output_path=...)`.
  Clash policy mirrors Tableau: identical definition = skip; same name different formula = import renamed (`name (2)`), report it;
  `overwrite` and `fail` are extra. Map the library's required fields onto the target datasource with the **same matcher**
  as `suggest_mapping` (do not fork it); unmapped fields fail the entry and everything that depends on it (topological order,
  report skipped dependents).
- Parameters: set value/allowed values, retain `domain-type`; check name clash with existing parameters; datatype conflicts.
- Writer: add `<column ... caption=... role=... type=... ><calculation class='tableau' formula='...'/></column>` the way
  `rename._new_column` and the corpus show; copy the exact attribute set from real corpus calcs. Parameters live in
  the `Parameters` datasource; there is no `[Parameters]` column duplication to forget (check `rename._drop_parameters`).
- LOD/table calcs reference dimensions by name: include them in `refs` and test with LOD, table calc, nested calc,
  calc using a parameter, calc using a set.
- CLI: `py-tbparse library export WB [--folder X] -o lib.json`, `library import WB lib.json [--on-clash ...] --write`, `library show lib.json`.
- Tests: dependency order, clash policies, unmapped dependency chain skipped, parameter round trip, output re-parses with
  `TwbParser` and `field_usage` shows the imported calc, corpus smoke test (export all calcs of every public workbook, re-import into itself = all skipped-identical).

### WP7. Style templates: palettes, fonts, formatting (backlog)

Goal: the "style guide workbook" made executable.

- **Phase 0, research (deliverable is a doc, no code)**: from the corpus catalogue where style lives:
  workbook `<style>`/`<style-rule element='...'>` (workbook-wide fonts/colors), `<preferences><color-palette>` (custom
  palettes; Tableau's `Preferences.tps` uses the same `<color-palette name type>` elements), datasource-level styles,
  per-sheet `<table><style>`, `<format>` elements, dashboard `zone-style`, device layouts, the dashboard title/logo
  zones. Write `docs/style-model.md` listing each element, scope and what is safe to transfer.
- **Style manifest**: `*.style.json`: `{palettes: [...], fonts: {...}, workbook_rules: [...], dashboard: {background, padding, title zone}, sheet_defaults: {...}}`. Extraction from a style-guide workbook:
  `extract_style(parser) -> dict`; apply: `apply_style(parser_or_path, style, scope="workbook|dashboards|sheets", select=None, output_path=...)`.
- Options: **Preferences.tps export/import** (`style export-tps` / `style import-tps`): a shared palettes file users drop into
  their Tableau Repository. Lowest risk, highest visible value, ship this first inside WP7.
- Respect user overrides: never overwrite a format that a sheet set explicitly unless `--force`; report counts
  (applied/skipped/forced per scope), like rename reports.
- Combine with template apply: `apply_template(..., style=path)` and in `template make --with-style`.
- Out of scope: Power BI theme JSON conversion (maybe later as a pure data-conversion helper).
- Tests: palettes round trip; applying to a workbook with a custom sheet format keeps it; `.tps` file schema; corpus smoke

### WP8. Writer fidelity: byte-preserving output / normalised diff (backlog)

Why it is on a template roadmap: reviewability (PBIP lesson) and trust (users must see the template did only what it said).
- Minimum: `tests/helpers.normalised_diff(a, b)` canonicalising attribute order/quotes/whitespace (c14n via lxml
  `etree.tostring(method="c14n")`) so tests and a new CLI `py-tbparse diff-xml A B` show only real changes.
- Stretch: text-level patching of the original XML for the handful of edits we make (connection swap, `remote-name`,
  parameter values, captions). Only start if the owner wants it; measure first how many lines differ on the corpus.
- Acceptance for the minimum: `explain` (WP1) and the verification pack (WP0) use it.

### WP9. GUI Templates view (separate track; do not start until WP0 and WP1 are done and the owner confirms)

Belongs to `ui-redesign` phase 4 (see `/home/claude-user/ai-sandbox/py-tbparse-ui-redesign-plan.md` and `docs/ui-redesign-plan.md`
on that branch). The GUI should be a thin client over the API: choose template, choose data (CSV/xlsx/workbook, drag-and-drop;

## 4b. Additional candidate packages (research round 2, 2026-10-02)

Same caveats as 1.3: web-search summaries, hypotheses to confirm with the owner. These are **candidates**, not

### 4b.1 What already exists in the ecosystem (so we do not rebuild it badly)

- **Audit / lineage / docs (free, mostly browser-based)**: Tableau Workbook Auditor (dead fields, duplicate calcs, perf lint,
  diffs, dependency graphs; <https://github.com/andey0Saikiran/tableau-lineage>), TableauToDbt audit (health score 0-100,
  circular deps, division errors; <https://tableautodbt.com/audit>), TabLens (<https://www.tablens.net/>),
  tableau-reverse-engineering-catalog (per-workbook doc tree with "where used"; <https://github.com/guizaunzin/tableau-reverse-engineering-catalog>),
  tableau-workbook-documenter (design-doc Markdown; <https://github.com/konpuku/tableau-workbook-documenter>).
  Tableau's own **Workbook Optimizer** flags unused fields, nested calcs, hidden containers
  (<https://help.tableau.com/current/pro/desktop/en-us/wbo_overview.htm>).
  Gap we can fill: a **scriptable, CI-friendly Python/CLI** version that also *fixes* things (prune), not a browser viewer.
- **CI/CD**: GitHub Action for validating/publishing `.twb` (<https://github.com/marketplace/actions/tableau-workbook-action>),
  `tableau-deploy` (<https://github.com/byldworks/tableau-deploy>), BI Validator / Datagaps (commercial regression testing).
  Gap: pre-publish **static checks with machine-readable output**; publishing itself is out of scope (outward-facing, needs credentials).
- **Tableau to Power BI conversion** (Pulse Convert, BIChart, Kanerika FLIP, Sparity): all commercial, AI-assisted LOD-to-DAX.
  Not a fit for this project; at most a *migration-readiness census* (see WP15).
- **Localization**: BabelViz, DooLittle Translate (commercial); free approaches are manual caption edits or a translation-table
  data source with a language parameter (<https://tableauandbehold.com/2015/08/20/full-localization-of-tableau-workbooks/>). Gap: free, offline, round-trippable string export/import.
- **Programmatic connection edits**: Tableau Document API (unsupported; cannot edit fields, `.twbx` handling is weak),
  forum recipes for changing the server name across many workbooks (<http://tableaufriction.blogspot.com/2012/12/changing-database-server-name-in.html>), Migration SDK transformers (server-side only).
- **Merging workbooks**: Tableau has **no merge feature**; only copy/paste of sheets/dashboards (data sources, calcs, parameters,
  sets come along; hidden sheets of a dashboard too) (<https://help.tableau.com/current/pro/desktop/en-us/copy_b_wkbks.htm>, <https://interworks.com/blog/kkain/2017/08/21/combine-your-projects-workbook-merge/>).
- **Version compatibility**: newer workbooks do not open in older Desktop; "Export As Version" goes back only to 10.5; editing the
  `version` attribute by hand does not remove newer features and breaks the file (<https://help.tableau.com/current/pro/desktop/en-us/publish_version_compatibility.htm>).
- **Wildcard union** of files/sheets is how Tableau users absorb new monthly files; schema drift breaks it (<https://help.tableau.com/current/pro/desktop/en-us/union.htm>).
- **Dashboard-as-code** in Grafana (Grafonnet/jsonnet with per-tenant external variables) has no Tableau equivalent found
  (<https://github.com/heroku/grafonnet-lib>). Tableau authors reuse layouts with template workbooks, device layouts, nav buttons, sheet swapping (<https://www.techtipsgirl.com/post/layout-schmayout-use-tableau-template>).

### 4b.3 Detail for the packages most worth doing next

**WP19 Template tokens** (do right after WP1; makes WP4 batch far more useful)
- Manifest `tokens: [{name, default, where: ["dashboard:Title", "sheet:Sales caption", ...]}]`. Tokens are written by the template author as literal
  `{{name}}` text; `make_template` scans captions, titles, text zones, parameter defaults and records them.
- `apply_template(..., tokens={"customer": "ACME"})`, also in answers/profile and the sidecar CSV of WP4. Unfilled token with no default = `TemplateError` listing where it occurs.
- Escape syntax `{{{{` for literal braces; tokens are plain text only (never inside formulas, to avoid breaking calcs; if found in a formula, `make` warns).
- Tests: every location kind, escaping, missing token, token inside a calc (warning), non-Latin values, XML-special characters in values.

**WP12 Sanitize**
- `sanitize(parser_or_path, output_path, keep=("captions",), fake_data=False, report=None)` and `py-tbparse sanitize WB -o OUT`.
- Scrub: connection attributes (`_CONNECTION_ATTRS`, `_SECRET_ATTRS`), local file paths, custom/initial SQL text (replace with placeholder, keep a list in the report), extracts, `<repository-location>`, user filters/`USERNAME()` references (warn, do not rewrite), comments/annotations, thumbnails in the twbx.
- `fake_data=True`: generate a small CSV per datasource from the manifest-like field list (type-aware synthetic values, seeded) and connect to it so the workbook opens and renders; clearly mark as synthetic. Reuse `_csv_connection`.
- Report lists exactly what was removed; test that no original server/db/user string survives in any member of the output zip (search bytes of every zip member, including thumbnails).

**WP10 Audit and prune**
- Rules (each a function returning rows `{rule, severity, object, detail, fix}`): unused field, unused calc, duplicate calc (normalised formula), nested calc depth over N, circular dependency, calc referencing missing field, parameter unused, sheet unused in any dashboard, hidden-but-used field, empty datasource, custom SQL present, extract leftovers, absolute paths, fields with default names (`Calculation_123`), long formulas, division without zero guard (heuristic, label as such).
- `audit(parser) -> DataFrame` + score; `prune(parser, rules=("unused-fields",), dry_run=True)`: remove only what `field_usage` proves is unused, and **only hide-vs-delete as Tableau does** (Tableau's own advice is "hide all unused fields"): default to `hidden="true"`, delete only with `--delete`.
- CLI: `py-tbparse audit WB [--min-score N] [--format table|json|junit]`, `py-tbparse prune WB --write PATH`.
- Tests on corpus: no crash on 200 workbooks, deterministic ordering, prune followed by `validate` finds no new problems, prune is idempotent.

**WP13 Localization**
- `export_strings(parser) -> DataFrame[id, kind, context, source_text, max_length_hint, notes]`; `import_strings(parser, table, locale, output_path)`; CLI `py-tbparse l10n export|import`. Kinds as listed in 4b.2. Keep an `id` stable across revisions (hash of kind + owner + original text) so a translation survives small edits.
- Do not translate field **names** that formulas depend on; translate captions only (captions are display text). Calculated-field string literals are listed as `kind=literal` but not rewritten unless `--literals` (risky).
- Round-trip test: export, import the same text = byte-identical normalised XML (needs WP8 helper); import with a pseudo-locale (`[!! text !!]`) to catch truncation.
